## Claims

- Up to 10 developer test accounts can be created per standard HubSpot account; they are free, carry a 90-day trial of many Enterprise features, expire after 90 days without API calls, and can be renewed manually or by API (no more than 30 days before expiry, with an OAuth token from an app in the same developer account) [hubspot-docs-test-accounts §Developer test accounts].
- Developer test account limits: marketing emails only to users added to the account, Content Hub caps (25 website pages, 1 blog with up to 100 posts, 25 landing pages), workflows enrol up to 100,000 records per day with extra enrolments dropped, and test accounts cannot sync data with other accounts [hubspot-docs-test-accounts §Developer test accounts].
- Configurable test accounts (platform 2025.2+, CLI 8.3.0+) are created with `hs test-account create` from scratch or from a JSON config generated by `hs test-account create-config`, with one subscription tier per Hub (default: Enterprise trials for all Hubs); CRM data is loaded with `hs test-account import-data` from CSV plus JSON config, and custom properties must exist before import [hubspot-docs-config-test-accounts §Create from a config file].
- Standard sandboxes require Enterprise (Marketing, Sales, Service, Data, Content, Smart CRM or Revenue Hub) and Super Admin; they copy production's features and supported assets at creation, with Super Admins and developer-tool users copied, and optionally the 5,000 most recently updated contacts with up to 100 associated deals, companies and tickets each [hubspot-kb-sandbox §Create a standard sandbox].
- In a standard sandbox, record IDs differ from production, production integrations are not connected automatically (HubSpot recommends connecting each integration's sandbox version), workflows copy only if their dependent assets copy, up to 200,000 records per object type can be imported, workflows enrol at most 100,000 records per day, and email only sends to addresses shared with sandbox users [hubspot-kb-sandbox §Sandbox best practices].
- Sandbox-to-production deployment is a one-time push of up to 300 supported asset changes, cannot be cancelled once started, and is not supported from legacy sandboxes (unsupported since April 30, 2026) [hubspot-kb-sandbox §Set up a production deploy].
- Development sandboxes also require Enterprise, are created and managed only through the CLI, and CMS sandboxes are free but unconnected to the standard account [hubspot-docs-test-accounts §Sandbox accounts].
- Webhook target URLs must be publicly reachable over HTTPS, and a sample-payload and testing feature exists in the app's webhook settings [hubspot-docs-webhooks §Limits; hubspot-docs-webhooks-projects §View webhook subscriptions in HubSpot].
- Newly created or updated records take "a few moments" to appear in CRM search results [hubspot-docs-search §Paging through results].

## Implications for the build

- Develop against a configurable developer test account seeded with `hs test-account import-data`: create the scorer's custom properties first, then import synthetic contacts, companies, deals and meetings; this costs nothing and does not need Enterprise.
- For pre-production, use a standard sandbox with the 5,000-contact copy to test against realistic property schemas and pipelines, but remember IDs differ from production, so the service's configuration (owner IDs, pipeline/stage IDs, property names) must be environment-specific and loaded at start-up from the APIs, never hard-coded.
- Use a tunnel (public HTTPS) for local webhook testing and HubSpot's sample-payload tester; for CI, replay recorded webhook batches (arrays of up to 100 events, with duplicates and out-of-order `occurredAt`) against the handler, since there is no local HubSpot emulator.
- Mock the API at the HTTP layer with recorded fixtures for: contact/company/deal reads, batch update 200 and 207 responses, 429 with rate-limit headers, and search pages with `paging.next.after`; include the search indexing delay in integration tests (write, then expect the record to be absent from search for a moment).
- Keep the test account alive by scheduling a trivial API call well inside the 90-day window, and plan to re-create it when trials lapse; sandbox email restrictions mean alert emails must be tested with addresses matching sandbox users.
- Treat production deployment of HubSpot-side assets (properties, workflows) as a separate release step from the Python service deploy; the sandbox deploy is one-way and uncancellable.
